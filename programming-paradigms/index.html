1Introduction

What is a programming paradigm?

programming paradigm noun

A style, or approach, to programming. It is based on a set of ideas about how a program should be organised and how it runs (Van Roy, 2009).

A paradigm isn't a programming language. It's a way of thinking about a problem: how to split it up, where the data is kept and what decides the order the code runs in. Many languages support more than one paradigm. Python, for example, can be written in all three styles in this presentation.

The three paradigms in this presentation

2Procedural · what it is

Procedural programming

procedural programming noun

A style of programming where a program is a list of instructions that the computer carries out in order, from top to bottom. The instructions are grouped into procedures (also called functions or subroutines) that can be called whenever they're needed (Sebesta, 2016).

a type of imperative programming · e.g. C, Pascal, BASIC, Fortran, COBOL, or Python written this way

Key features

  • Sequence, selection, iterationSteps in order, decisions with if, and loops with for and while.
  • Procedures (functions)Named blocks of code that each do one job and can be called again and again.
  • Parameters and return valuesData goes into a procedure as parameters, and the answer comes back with return.
  • Local and global variablesLocal variables only exist inside their procedure. Global ones can be used anywhere.
  • Top-down designA big problem is broken down into smaller procedures (decomposition).
  • Data is kept separateData is passed from procedure to procedure. It doesn't belong to any of them.

2Procedural · code example

Example: adding up the basket

basket_procedural.pyPython 3

# Procedural: a list of steps, split into functions

def add_up(prices):              # a procedure (function)
    total = 0                    # a local variable
    for price in prices:         # iteration (a loop)
        total = total + price
    return total                 # send the answer back

def apply_offer(total):
    if total >= 5:               # selection (a decision)
        total = total - 1        # £1 off orders of £5+
    return total

basket = [1.25, 3.50, 0.75]      # croissant, sourdough, cookie
subtotal = add_up(basket)        # call the function
to_pay = apply_offer(subtotal)
print(f"To pay: £{to_pay:.2f}")

Procedural: pros, cons and where it's used

          

          

        

        

          

            

              
basket.cC

              
#include <stdio.h>

float add_up(float prices[], int count) {
    float total = 0;
    for (int i = 0; i < count; i++) {
        total = total + prices[i];
    }
    return total;
}

int main(void) {
    float basket[] = {1.25, 3.50, 0.75};
    printf("Total: %.2f\n", add_up(basket, 3));
    return 0;
}

              
OutputTotal: 5.50

            

            
The same add_up() in C, a classic procedural language. A C program is just functions and data, with no classes or objects (Kernighan and Ritchie, 1988).

          

          

            

              
+Advantages

              
    
                
  • Easy to follow. The code runs in the order you read it, so it's a good way to learn.
    • 
                
  • Fast and light. There's little extra code, so it suits scripts and small devices.
    • 
                
  • Reusable functions. A function can be called many times and tested on its own.
    • 
              

            

            

              
−Disadvantages

              
    
                
  • Hard to manage when it grows. Hundreds of functions and global variables get messy.
    • 
                
  • Data isn't protected. Any function can change a global variable by mistake.
    • 
                
  • Not a natural fit for real things. A customer or a product is just loose data.
    • 
              

            

            

              
Where it's used

              
    
                
  • scripts & automation
    • 
                
  • calculations & data processing
    • 
                
  • embedded systems (Arduino)
    • 
                
  • operating systems (Linux is mostly C)

3Event-driven · what it is

            
Event-driven programming

          

          

        

        

          

            

              
event-driven programming noun

              
A style of programming where the flow of the program is decided by events: things that happen, like a click, a key press, a sensor reading or a timer running out. The program waits for events, and when one happens it runs the code linked to it, called an event handler (MDN Web Docs, no date a).

              
e.g. Visual Basic, C# with Windows Forms, JavaScript, Python with tkinter

            

            
Key features

            
    
              
  • EventsUser actions (click, key press), sensors, timers or messages from other programs.
    • 
              
  • Event handlersFunctions that run when a certain event happens (also called callbacks).
    • 
              
  • Listeners (triggers)Code that links an event on an object, like a button, to its handler.
    • 
              
  • The event loopRuns all the time, waiting for the next event and sending it to the right handler.
    • 
              
  • An event queueEvents that arrive together wait in a queue and are handled one at a time.
    • 
              
  • The user is in controlUsually there's a GUI with buttons and menus. The user decides what happens next.
    • 
            

          

          
        

      

    

  


  
  

    

      

        

          

            
3Event-driven · code example

            
Example: a bakery till with a button

          

          

        

        

          

            
till_events.pyPython 3 · tkinter

            
import tkinter as tk

total = 0                            # a global variable

def add_croissant():                 # event handler
    global total
    total = total + 1.25
    label.config(text=f"Total: £{total:.2f}")

def clear(event):                    # event handler
    global total
    total = 0
    label.config(text="Total: £0.00")

window = tk.Tk()                     # set up the window
window.title("Bakery till")
label = tk.Label(window, text="Total: £0.00")
label.pack()
button = tk.Button(window, text="Add croissant",
                   command=add_croissant)  # click → handler
button.pack()
window.bind("c", clear)              # key press C → handler

window.mainloop()                    # event loop: wait for events

      4Object-oriented · what it is
      
            
      Object-oriented programming (OOP)
      
          
      
          
      
        
      
        
      
          
      
            
      
              
      object-oriented programming noun · OOP for short
      
              
      A style of programming where the program is built from objects. Each object keeps its own data (attributes) together with the actions that use that data (methods). Objects are made from classes, which work like blueprints (Oracle, no date).
      
              
      e.g. Java, C#, C++, Python, Ruby, Kotlin
      
            
      
            
      
              
      Class
      The blueprint for making objects, e.g. Product.
      
              
      Object
      One thing made from a class, also called an instance, e.g. croissant.
      
              
      Attribute
      A piece of data an object keeps, e.g. its name and price.
      
              
      Method
      A function that belongs to an object, e.g. describe().
      
              
      Constructor
      The method that sets up a new object: __init__() in Python.
      
            
      
          
      
          
        
      
        
      
          
      The four main ideas of OOP (Booch et al., 2007)
      
          
        
            
      • EncapsulationData and methods are kept together in an object. Data can be private, so only the object's own methods can change it.
        • 
            
      • InheritanceA child class gets the attributes and methods of a parent class and can add its own, e.g. a Cake is a Product.
        • 
            
      • PolymorphismThe same method name does different things in different classes, e.g. describe().
        • 
            
      • AbstractionOnly show what's needed to use an object and hide the details, e.g. you call basket.add() without seeing how it works.
        • 
          
      
        
      
      
      
    
      
  
      

  
  
      
    
      
      
      
        
      
          
      
            
      4Object-oriented · code example
      
            
      Example: products and a basket as objects
      
          
      
          
      
        
      
        
      
          
      
            
      basket_oop.pyPython 3
      
            
      class Product:
    def __init__(self, name, price):   # constructor
        self.name = name               # attributes
        self.price = price

    def describe(self):                # a method
        return f"{self.name} costs £{self.price:.2f}"

class Basket:
    def __init__(self):
        self.items = []
        self.total = 0

    def add(self, product):            # a method
        self.items.append(product)
        self.total = self.total + product.price

croissant = Product("Croissant", 1.25) # objects
sourdough = Product("Sourdough", 3.50)
basket = Basket()
basket.add(croissant)
basket.add(sourdough)
print(croissant.describe())            # Croissant costs £1.25
print(basket.total)                    # 4.75

        Inheritance, polymorphism, pros and cons

        products.pyPython 3
        
              
        class Product:
    def __init__(self, name, price):
        self.name = name
        self.__price = price             # private (encapsulation)

    def get_price(self):                 # the way to read it
        return self.__price

    def describe(self):
        return f"{self.name}: £{self.__price:.2f}"

class Cake(Product):                     # inherits from Product
    def __init__(self, name, price, slices):
        super().__init__(name, price)    # Product's constructor
        self.slices = slices             # an extra attribute

    def describe(self):                  # overrides describe()
        return f"{self.name} cake, {self.slices} slices"

items = [Product("Croissant", 1.25), Cake("Lemon", 12, 8)]
for item in items:
    print(item.describe())               # polymorphism
print(items[1].get_price())              # inherited from Product

        +Advantages
        
              
          
                
        • Organised. Each class looks after its own data and job, which suits big programs and teams.

        5Comparison
        
          
        How they fit together
        
          
        The three paradigms aren't rivals. Most real programs use all three at the same time, like this version of my till. The coloured lines show which paradigm each part of the code belongs to.
        
        
        
        
        
          
        
            
        till_app.pyPython 3 · tkinter
        
            
        import tkinter as tk

class TillApp:                                # a class
    def __init__(self, window):
        self.total = 0                        # an attribute
        self.label = tk.Label(window, text="Total: £0.00")
        self.label.pack()
        button = tk.Button(window, text="Add croissant",
                           command=self.add)  # click → handler
        button.pack()

    def add(self):                            # a method + event handler
        self.total = self.total + 1.25        # step 1
        if self.total >= 5:                   # step 2: a decision
            self.label.config(fg="green")
        self.label.config(text=f"Total: £{self.total:.2f}")

window = tk.Tk()
app = TillApp(window)                         # an object
window.mainloop()                             # the event loop

        6Conclusion
        
          
        Conclusion
        
          
        A paradigm is a way of organising a program. Procedural programming is about the steps, event-driven programming is about when the code runs, and object-oriented programming is about how the code and data are grouped together.
        
        
        
        
          
          
        • 
            
          Procedural
          
            
          
              
          In one line
          Steps in order, grouped into functions.
          
              
          Think of it as
          A recipe.
          
              
          Best for
          Small programs, scripts and calculations.
          
            
          
          
          • 
          
        • 
            
          Event-driven
          
            
          
              
          In one line
          Waits for events and runs a handler for each one.
          
              
          Think of it as
          A shop assistant waiting for customers.
          
              
          Best for
          Anything with buttons, keys or sensors.
          
            
          
          
          • 
          
        • 
            
          Object-oriented
          
            
          
              
          In one line
          Objects made from classes, each with its own data and methods.
          
              
          Think of it as
          The bakery's real things, each with its own job.
          
              
          Best for
          Big programs that need to stay organised.
          
            
          
          
          • 
        
        
        
        
          
        Which one I would use
        
          
        For a quick calculation I'd write procedural code. As soon as there's a window with buttons, I need event-driven code. Once a program grows, I'd organise it into classes. In Python I can do all three in the same program, like the till on the last slide.
        
          
        my opinion: learn procedural first, because the other two are built on top of it
